# M2b: observed pass on codex-cli 0.164.0-alpha.11.1 (2026-10-26)

Scope: one existing, long-running native Codex Goal in the desktop app
26.1021.3705.0, not a new test Goal. The goal ID, thread ID, objective,
message text, auth, process paths, and per-user content are not recorded.

After the engine updated, the previous Core-only `codex queue` continuation
completed, but the same native Goal remained `usage_limited`. Read-only Codex
goal database and `thread/goal/get` agreed; the target conversation was held
by the Desktop, its most recent turn had completed, and its queue was empty.

The existing Advanced M2b route then performed **one** guarded live attempt:

1. Set that same Goal `active` via `thread/goal/set` (status only, no objective).
2. Read the same goal ID back as `active` from Codex's database.
3. Added **one** continuation via `thread/queue/add`, with one unique
   clientUserMessageId. Codex returned an accepted queue receipt.
4. Observed the queued item consumed, the next native turn `inProgress`, and
   the original Goal still `active`.

The one-attempt identifier, state snapshots and SQLite backups are kept
locally outside the repository. A first conservative preflight detected three
historical stale `inProgress` rows, older than the latest completed turn, and
aborted without sending; the successful attempt excluded those stale rows
while guarding against any newer running turn, queue or Auto Resume claim.

This is evidence for M2b on this **exact** Codex version only, not a blanket
permission for new versions. The run was not a completed end-to-end proof of
the Goal's eventual objective; limits and future updates still need observing.
