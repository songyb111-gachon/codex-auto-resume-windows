# 개발 과정

> 🌐 한국어 문서입니다. English version: [`main` 브랜치의 docs/DEVELOPMENT.md](https://github.com/songyb111-gachon/codex-auto-resume-windows/blob/main/docs/DEVELOPMENT.md)

이 프로젝트는 한 명의 인간 제작자가 두 개의 AI 코딩 도구와 함께 다섯 단계(0부터 4까지)에 걸쳐 만들었습니다. 이 문서는
v0.5 릴리스까지의 작업을 다루며, 그 뒤의 일은 [CHANGELOG.ko.md](CHANGELOG.ko.md)와 [ROADMAP.ko.md](ROADMAP.ko.md)에 있습니다. 여기에
기록하는 이유는 **조사 과정 자체가 이 프로젝트 가치의 큰 부분**이기 때문입니다. 대부분의 노력은 Windows
ChatGPT/Codex 데스크톱 앱이 실제로 무엇을 지원하는지 알아내고, 무엇을 **지원하지 않는지** 증명하는 데
들어갔습니다.

링크된 증거 파일의 식별자는 가명화되어 있고 절대 경로와 프로세스 ID는 일반화되어 있습니다. 대화 내용,
프롬프트 전문, 자격 증명은 로컬 기기를 벗어난 적이 없습니다.

그때의 발견들과 그 위에 쌓아 올린 모든 것이 *지금* 무엇으로 뒷받침되는지는 기능별로
[FEATURE_MATRIX.ko.md](FEATURE_MATRIX.ko.md)에 적혀 있고, 그중 실제 기계 앞의 사람만 매듭지을 수 있는 부분은
[LIVE_ACCEPTANCE.ko.md](LIVE_ACCEPTANCE.ko.md)의 절차입니다.

## 0단계 — 목표와 안전 제약 (songyb111-gachon)

제작자가 문제, 아키텍처 방향, 그리고 가장 중요하게는 이후 모든 결정을 규정한 안전 제약을 정의했습니다.

- 로컬 전용. 외부 서버 없음, 텔레메트리 없음, 저장소나 대화 데이터 업로드 없음.
- Codex 자체 상태에 대해 읽기 전용. Codex 데이터베이스에 절대 쓰지 않음.
- **정확한** 중단 스레드를 재개. `--last` 금지, 추측한 스레드 금지.
- 같은 중단을 두 번 재개하지 않음.
- 불확실하면 멈춤: 모호함은 전송하지 *않는* 결과로 이어져야 함.
- 명시적으로 범위 밖: GUI 자동화, 마우스·키보드 흉내, OCR, 화면 스크래핑, 접근성 API 클릭, 바이너리 패치,
  DLL 인젝션, 프로세스 메모리 조작, 자격 증명 추출.

이것들은 선호가 아니라 **불변 조건**으로 취급되었습니다.

## 1단계 — 조사 (OpenAI Codex)

Codex가 Windows ChatGPT 데스크톱 앱과 그 Codex 엔진의 실제 동작을 조사했습니다.

- 데스크톱 앱은 별도의 `codex.exe` 엔진 프로세스를 자식으로 실행하며 stdio로 연결합니다.
- 로컬 상태는 Codex 홈 디렉터리에 있습니다. 스레드 메타데이터, 페이지네이션된 턴/아이템 기록, 큐
  데이터베이스, JSONL rollout 파일, 그리고 스레드별 쓰기 잠금 파일입니다.
- 공식 CLI는 정확히 한 스레드를 대상으로 하는 `codex queue --thread <UUID>`를 제공합니다.
- 설치된 바이너리에서 app-server 프로토콜 스키마를 생성해 대응하는 업스트림 릴리스 태그와 비교했습니다.
  덕분에 어댑터는 추측이 아니라 검증된 버전에 고정되어 있습니다.

## 2단계 — 되는 것과 안 되는 것 증명 (OpenAI Codex)

두 실험 모두 **일회용 테스트 스레드**로만 수행했고, 실제 대화는 건드리지 않았습니다.

**로드된 스레드: 됨.** 앱에 스레드가 이미 로드된 상태에서 `codex queue --thread <UUID>` 한 번 호출이 그
정확한 대화에 실제 사용자 메시지로 전달되었고 에이전트가 응답했습니다. 증거:
[`evidence/loaded-thread-delivery.json`](evidence/loaded-thread-delivery.json).

**미로드 스레드: 안 됨.** 실제로 앱을 재시작하고 대상 스레드가 `notLoaded`임을 확인한 뒤, 큐에 넣은 메시지
한 건이 90초 관찰 내내 큐에만 남아 있었고 대화 턴이 되지 못했습니다. 테스트 큐 항목은 이후 공식 API로
제거했습니다. 증거: [`evidence/unloaded-thread-delivery.json`](evidence/unloaded-thread-delivery.json),
[`evidence/unloaded-thread-observation.json`](evidence/unloaded-thread-observation.json).

이것이 이 제품의 핵심 제한이 생긴 이유입니다. 문서화된 발견이지 버그가 아닙니다.

**사용량 한도의 형태.** 실제 사용량 한도 중단을 읽기 전용으로 포착했습니다. 해당 턴은 `status=failed`와
`codexErrorInfo=usageLimitExceeded`로 기록되고, 바로 앞의 요청 제한 스냅숏이 UI에 표시된 시각과 분 단위로
일치하는 숫자형 재설정 시각을 담고 있었습니다. 특히 원본 rollout 이벤트 이름이 `task_complete`인데도
오류를 함께 담고 있으므로, **이벤트 이름만 보고 성공으로 판단해서는 안 됩니다.** 정제된 샘플:
[`evidence/usage-limit-sample.json`](evidence/usage-limit-sample.json).

2단계가 끝난 시점에 Codex는 감지기, 영속 저장소, Windows 어댑터, 최초 스케줄러와 테스트 65개를
만들어 두었습니다. 그 작업은 이 저장소의 첫 커밋에 보존되어 있습니다.

## 3단계 — 완성 (Anthropic Claude Code)

Claude Code가 미완성 프로토타입을 인수해 검토하고, 건전한 부분은 유지한 채 완성했습니다.

인수받은 코드에서 종단간 실행을 해봐야만 드러나는 잠복 버그 두 건을 발견했습니다.

- `collect()`가 감지기 출력을 그대로 저장소에 넘겼는데, 여분 키 두 개 때문에 저장소가 이를 거부했습니다.
  결과는 치명적이었습니다. **어떤 중단도 등록되거나 재개되지 않았습니다.** 워처는 "detection skipped"만
  영원히 기록했습니다.
- 진입점이 `sys.exit()` 없이 `main()`을 호출해 모든 종료 코드가 0이 되었고, 단일 인스턴스 "busy" 신호가
  보이지 않았습니다.

이 단계에서 추가된 것: 워처 루프, 전체 CLI, 프롬프트를 기록하지 않는 회전 로그(`errors.log`에는 이
도구가 쓰지 않은 예외 문구가 담깁니다. `PRIVACY.ko.md` 참고), 선택적 사용자별 Windows 자동 시작,
깨끗한 제거, 설정 및 바이너리 탐색, 그리고 테스트 모음의 대폭 확장.

## 4단계 — 검토와 적대적 감사 (Anthropic Claude Code)

세 차례의 검토를 수행했습니다. 각 회차는 차원별로 독립 리뷰어를 여러 명 두고, 이어서 세 명의 추가 독립
에이전트에게 모든 발견을 *반증*하도록 시켰습니다. 반증을 견딘 발견만 수정했습니다.

| 회차 | 범위 | 확인 | 반증 |
|---|---|---:|---:|
| 1 | 감지기, 저장소, Windows 어댑터, 스케줄러 | 12 | 6 |
| 2 | CLI, app, config, 로깅, 자동 시작 | 3 | 0 |
| 3 | 9개 차원 최종 감사 | 8 | 3 |

확인되어 수정된 대표적 문제들:

- 로드 상태 프로브가 바이트 범위가 순간적으로 비었을 때 **앱 자신의 배타적 스레드 쓰기 잠금을 획득**할 수
  있었고, 이는 앱 자체의 잠금 시도를 실패시킬 수 있었습니다. 잠금 코드를 통째로 제거하고, 소유 판정은
  재시작 관리자 목록만으로 하게 했습니다.
- `install --startup`이 환경변수로 설정된 홈 디렉터리를 누락해, 자동 시작된 워처가 다른 상태
  데이터베이스와 **다른 단일 인스턴스 뮤텍스**를 쓰게 만들었습니다.
- 제거가 자기가 만들지 않은 동명 파일을 지울 수 있었습니다. 이제 소유 표시 파일을 요구하며, 직접 만들지
  않은 디렉터리는 건드리지 않습니다.
- 로그인 시점의 일시적 엔진 프로브 실패가 워처를 세션 내내 종료시켰습니다.
- NTFS 정션이 디렉터리 봉쇄 검사를 우회했습니다. `is_symlink()`가 정션을 감지하지 못하기 때문입니다.

반증된 발견도 기록해 둡니다. 예를 들어 "임의로 오래된 실패가 재개될 수 있다"는 주장은 반증되었습니다.
재개하려면 그 실패한 턴이 여전히 해당 스레드의 최신 턴이어야 하고, 전송 직전에 실시간 사용량 가용성을 다시
확인하기 때문입니다.

코드 검토 외에 세 가지 실증 기법을 사용했습니다.

- **뮤테이션 테스트.** 안전 가드 약 20개를 의도적으로 망가뜨려 테스트가 잡아내는지 확인했습니다. 살아남은
  3건이 실제 테스트 공백을 드러냈고 모두 제거 안전성 영역이었으며, 회귀 테스트를 추가했습니다. 이 과정에서
  `store.reserve()`의 가드 하나는 **없으면 실제로 이중 전송이 가능**함이 증명되었습니다.
- **충돌 구간 매트릭스.** 전송을 둘러싼 네 지점(예약 직후, CLI 실행 전, 전달 후 기록 전, 큐 등록 후 기록
  전)에서 프로세스를 강제 종료했습니다. 재시작 후 모든 경우에서 전송은 최대 1회였습니다.
- **교차 프로세스 경쟁.** 네 개 프로세스가 같은 중단 건을 두고 여덟 번 경쟁했고, 매번 정확히 하나만
  성공했습니다.

## 번들 Python을 옮기는 날

이 페이지의 나머지는 기록이고, 이 절은 점검표입니다. 번들 런타임은 일부러 고정되어 있으며 누군가 그렇게 정했을 때만
옮겨 갑니다. 아래 내용은 런타임을 3.14에 둔 채 3.15.2에 대고 미리 시험했으므로, 3.15로 옮기는 일은 `dev`에서 한 번의
변경으로 이 목록을 처리하는 것이 전부입니다.

1. **고정값.** `build/make_release.py`의 `PYTHON_VERSION`과 `PYTHON_SHA256`(다이제스트는 python.org 릴리스 파일 목록에서 옮겨
   적고 실제로 받은 파일과 비교합니다). `scripts/python_support.json`의 `bundled_runtime`과 `release_build`, 그리고
   `tests/test_python_support.py`가 그것과 맞추어 지키는 `.github/workflows/`의 정확한 버전 세 곳(`release.yml` 둘, `test.yml`
   하나). `tests/test_python315_switch.py`의 고정(커밋된 목록은 아직 3.14의 것)도 함께 바꿉니다.
2. **런타임에 남길 것.** `python build/runtime_keep.py <embed zip> --python X.Y.Z --sha256 <digest> --out <파일>`을 실행한 뒤
   그 파일을 `build/runtime_keep.json` 위에 복사합니다. 도구는 버전이 붙은 이름을 바꾸고, zip에 아직 있는 것을 남기고, 배포되는
   모듈이 없어서 실패하는 것을 더하고, 아직 맞는 사유를 옮겨 적습니다. "to read" 아래에 찍히는 것(있는 동안 종료 코드는 3)은
   제거된 모듈을 가져오는 import입니다. 읽어 보고 실행될 수 없는 이유를 `reviewed`에 적거나 그 모듈을 남기세요. 읽지 않은 것이
   남아 있으면 빌드 자체 검사가 멈춥니다. 3.15.2에서는 349개를 남기고, 파일 14개가 빠지고, `sre_*`는 zip에서 사라졌으며,
   `zipfile/_path/_functools.pyc`가 더해졌고, 읽어야 할 import는 `importlib.metadata`의 `_context`와 `_typing`,
   `sqlite3.__main__`의 `_completer`, `xml`의 `xml.utils`, `zipimport`의 `_zstd`입니다.
3. **CI.** 할 일 없음: 3.15 레인은 이미 병합을 막습니다(`test.yml`의 `experimental: false`).
4. **지연 import.** `src/codex_auto_resume/__init__.py`의 `LAZY_IMPORTS`이며 이날까지 꺼져 있습니다. 제품이 띄우는 인터프리터는
   세 언어, 여덟 곳의 명령줄 어디서 시작하든 이 패키지를 가장 먼저 가져오므로 이 한 곳에 둡니다. 켜면 번들 런타임의 모든 import가
   이름을 처음 쓸 때까지 미뤄집니다. 소스 실행은 그대로이고, 없는 모듈이 가져온 것처럼 통과하지 않도록 `build/runtime_check.py`는
   이를 거부합니다. 콜드 스타트, 일하는 중인 노트북에서 20회 중앙값:

   | | 3.14.10 | 3.15.2 | 3.15.2, 지연 |
   |---|---|---|---|
   | 브리지 호출 한 번(`controlcli status`) | 702 ms | 626 ms | 449 ms |
   | MCP 서버의 첫 응답 | 626 ms | 595 ms | 410 ms |
   | 감시기 한 틱(`run --once`) | 930 ms | 967 ms | 650 ms |

   창의 오래 사는 브리지는 창을 열 때 한 번, 일회성 호출은 매번 이득을 봅니다. `tests/test_python315_lazy.py`는 3.15에서 켠 경우와
   끈 경우의 모든 모듈 표와 브리지 응답을 비교하며 차이는 없고, import 시점에 다른 모듈에 등록하는 코드도 없습니다. 대가는, 오래
   사는 프로세스(감시기, MCP 서버)가 시작하고 몇 시간 뒤에, 업데이트가 바꿔 놓았을 수도 있는 파일에서 모듈을 가져온다는 점입니다.
   정식이 아니라 베타에서 켜고 그 첫 업데이트를 지켜보세요.
5. **문서.** 두 언어의 `docs/CHANGELOG.md` 항목, 그리고 `docs/GUIDE.md`, `docs/VERIFY.md`, `docs/CONTRIBUTING.md`가 적는 버전.

3.15가 저절로 바꾸는 것은 기본 텍스트 인코딩입니다(PEP 686). 인코딩을 적지 않은 텍스트 호출이 이런 PC에서는 cp949였지만 3.15에서는
UTF-8이 됩니다. 제품, 빌드, 테스트의 호출은 모두 인코딩을 적고, `tests/test_python315_encoding.py`가 적지 않은 새 호출을 찾아냅니다.
파이프도 바뀝니다. Python 자식은 이제 UTF-8로 출력하는데, `plugin_setup.py`와 `controlcli`가 스스로 그렇게 설정하므로 설치 프로그램과
창은 이미 그것을 기대합니다. 콘솔 프로그램(csc, PowerShell, cmd)은 여전히 코드 페이지로 출력하므로 `encoding="locale", errors="replace"`로
읽으며, 이는 3.15에서도 cp949입니다. 그냥 `text=True`로 두면 첫 한국어 단어에서 `UnicodeDecodeError`로 끝납니다.

`tests/test_python315_ready.py`는 3.15가 제거하거나 폐기 예정으로 둔 것을 막습니다. 3.15에서 시간이 어디에 쓰이는지 보려면
`build/profile_tachyon.py`가 임시 폴더에서 소스로 실행한 브리지나 감시기를 샘플링합니다(Tachyon, PEP 799). 배포되지 않습니다.
